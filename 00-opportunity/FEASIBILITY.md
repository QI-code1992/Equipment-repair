# Feasibility Candidate

状态：**Candidate / Awaiting user confirmation**（仅技术可行性初评，未批准 Stage 0）。

## 技术可行性（已有证据）

- 技术 SPEC 已选定 Python 3.13/FastAPI、PostgreSQL、MinIO/S3、Redis，并给出 10 人以内并发、100 台以内设备的演示规模假设。
- RAGFlow 负责文档解析/检索，LangGraph 负责受控路由、工具调用、人工确认；业务后端是唯一业务事实源和写入入口。
- 原型已覆盖故障上报、开始/结束维修、附件下载、维修记录双 Tab 等关键交互，可作为 MVP 验证载体。
- 自动化检查位于 `06-testing/tests/`，但这些是原型静态检查，不等于生产服务验收。

## 主要风险与缓解

| 风险 | 影响 | 缓解/门槛 |
|---|---|---|
| 没有稳定真实数据源（报警、故障码等暂不纳入） | 指标和预测价值受限 | 先锁定 40 项内置指标，验证数据覆盖后再扩展 |
| 模型/RAGFlow 返回幻觉或无引用 | 维修决策风险 | 白名单工具、引用强制、空检索明确报错、禁止伪结果 |
| 健康分规则/服务异常 | 错误风险统计 | 统一健康分服务，失败显示错误且不使用旧值兜底 |
| 设备授权或敏感数据泄露 | 合规与信任风险 | 服务端校验授权、审计、最小端口暴露和密钥隔离 |
| 集成与运维复杂度 | 交付延期 | Docker Compose 分离 RAGFlow 依赖；先做小规模试点 |

## MVP 验收与未知项

必须验证：故障闭环和 SLA、健康分规则一致性、授权拒绝、知识引用、合法指标问数及服务故障表现。仍未知：真实 API/遥测接入、数据质量、部署网络与合规要求、模型成本/延迟、并发和可用性目标、客户 ROI。
