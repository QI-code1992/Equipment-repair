# Stage 0 Opportunity Candidate

状态：**Candidate / Awaiting user confirmation**（未自批准 Stage 0）  
证据范围：当前有效 PRD、2026-07-13 对接结论、AI 技术 SPEC、现有原型交接文档。

## 机会摘要

新能源装载机的故障上报、维修闭环、知识检索和设备健康评分目前需要在同一运维平台中协同。现有材料已定义故障单状态（待接单/维修中/已处理）、SLA、维修记录、统一健康分服务，以及受控的智能问数和带引用的运维指导。机会假设是：把这些流程与受控 AI 结合，可减少人工查找和录入成本，并让维修决策有可追溯依据。

## 目标用户与业务痛点（证据支持）

- 一线维修人员：需要从故障上报进入维修、查看现场附件、填写处理结果；原型交接明确了开始/结束维修及附件证据流程。
- 运维/设备管理人员：需要查看设备台账、健康等级、故障和维修统计；PRD 要求工作台、BI、台账和详情统一读取健康分服务。
- 管理员/知识库维护者：需要上传、解析、重试、删除并审计知识文档；技术 SPEC 定义了 READY/FAILED 等状态和引用要求。
- 业务用户/管理者：希望用自然语言查询已内置指标；PRD 明确一期 40 项指标，模型不得生成数值。

## 价值假设（待验证）

若平台能在设备授权边界内提供可靠的故障闭环、健康风险视图和带引用的建议，则可缩短从发现故障到采取行动的时间、减少重复录入，并提高维修记录的可追溯性。具体节省工时、停机损失和付费意愿尚无市场或客户数据支持。

## 替代方案

已知替代方式包括人工/电话/表格流转、既有设备管理或工单系统、厂商售后系统，以及独立知识库或聊天工具。当前 workspace 没有竞品访谈、价格、采用率或客户流失数据，市场规模与差异化仍属未知。

## MVP 验证建议

以少量真实设备和维修人员做受控试点：验证故障上报至已处理闭环、健康分规则一致性、授权设备拒绝策略、知识检索引用完整性和 40 项指标问数准确性。试点前需用户确认目标场景、成功阈值、数据可用性与隐私边界。

## 开放问题

1. 首个付费客户/部署对象是谁，当前流程的量化成本（停机小时、人工时长、误报率）是多少？
2. 是否有真实设备遥测、故障和维修历史可用于试点，数据质量和接入责任由谁承担？
3. 目标部署规模、合规/网络要求、预算和采购决策链是什么？
4. 用户是否确认以上机会陈述并批准进入正式 Stage 0？
