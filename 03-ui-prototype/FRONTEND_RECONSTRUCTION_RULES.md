# 正式前端原型还原规范

## 1. 目的与适用范围

本规范适用于所有以 Stage 3 已批准原型还原、修改或验收的正式前端页面、应用壳、抽屉、弹窗、通知面板和悬浮 Agent。它不授权改变产品范围、接口、权限、数据模型或原型本身。

## 2. 原型真相源

- 唯一原型源码为 `03-ui-prototype/prototype/`；逐页 HTML 位于 `pages/*.html`，全局样式与交互位于 `assets/`。
- 正式实现唯一源码为 `codebase/frontend/`。不得复制、迁移或同步维护原型 HTML/CSS/JavaScript 到正式前端。
- 正式页面必须还原对应原型的页面范围、信息架构、模块顺序、卡片、组件、文案、字体层级、布局和关键交互；真实 API、权限、加载、空态和错误态只能替换原型演示数据，不能删除或新增原型视觉模块。
- 原型、PRD/SPEC、已批准变更之间冲突时，以项目负责人已批准的精确基线为准；不得为使实现通过而修改任一基线。

## 3. HTML 分析要求

实现前必须对对应原型 HTML 形成逐页对照清单，至少包含：页面壳、区块层级、组件/卡片、字段、按钮、表格列、状态、弹窗/抽屉、滚动容器、交互入口、资源与文本。

- 清单可更新 `06-testing/FRONTEND_PROTOTYPE_DIFFERENCE_MATRIX.md` 或同任务的设计/测试证据。
- 未被正式 API 支持的业务动作必须显示受控不可用或按已批准范围回流，不得用 mock 成功、静态业务数值或假入口掩盖缺口。

## 4. 截图与 Viewport 规范

- 每个页面至少在桌面 `1440 x 900` 截图；若原型定义了其他固定尺寸，以原型尺寸为准并同时记录。
- 页面包含移动或窄屏原型时，另按原型定义的目标 viewport 截图；没有对应原型时不得自行新增移动版视觉设计。
- 每次截图必须记录：原型文件、正式路由、目标 viewport、浏览器缩放 100%、精确 Commit SHA、截图时间和数据/权限状态。
- 截图文件与差异报告归档到 `06-testing/` 的对应页面证据目录，不提交浏览器缓存、临时 profile 或真实凭据。

## 5. 字体与 CSS 迁移

- 必须从对应原型的 CSS/设计 token 核对字体栈、字号、字重、行高、字色、背景、边框、圆角、阴影、间距、栅格及响应式断点。
- 优先复用正式前端已有的等价 token/组件；没有等价项时仅添加完成该原型还原所需的最小样式。
- 不得以通用 CSS 覆盖破坏其他页面的原型布局。跨页样式修改必须附受影响页面截图对照。
- 不得因技术便利引入新的视觉语言、渐变、卡片、字体、色彩体系或页面区块。

## 6. React 组件与资源规则

- React 组件边界应对应原型的稳定视觉/交互单元；不得为了单个页面新增无第二调用点的抽象层。
- 正式组件应保留正确语义、键盘可达性、焦点管理和对话框 `aria-modal` 行为。
- 图片、SVG、图标只可使用原型已有资源或项目已批准资源；应保留资源的内容、比例、清晰度与用途。不得用无关图标、临时占位资产或手绘 SVG 替代原型资产。
- 不得把接口 code、内部 ID、调试文本、原型注释、临时说明或未命名状态直接展示给用户；前端需提供已批准的中文显示映射。

## 7. 禁止修改项

- 不得新增、删除、合并或拆分原型页面、模块、卡片、字段、按钮、字体层级或关键交互，除非项目负责人通过变更台账明确批准。
- 不得修改 `03-ui-prototype/prototype/` 来适配正式实现。
- 不得修改真实 `.env`、密钥、运行卷、生成目录、`node_modules/` 或部署环境数据。
- 不得将“代码能编译”“单元测试通过”表述为“原型还原完成”或“视觉验收通过”。

## 8. 视觉验收与 Screenshot Diff

每个页面候选至少需要原型截图与正式实现截图的并列对照。对照必须逐项确认：

1. 页面与应用壳的可见范围、布局、列数、尺寸和滚动行为一致。
2. 标题、文案、字体层级、颜色、间距、边框、圆角和状态样式一致。
3. 原型中的卡片、表格列、按钮、弹窗/抽屉、浮层和交互入口均存在；原型外可见元素不存在。
4. 在目标 viewport 下没有裁切、重叠、被遮挡、溢出或不可达内容。
5. 正式数据、权限和错误状态未破坏原型信息结构。

截图差异工具可使用浏览器自动化或像素差异工具。若环境未提供可用工具，必须保留同 viewport 的人工并列截图和逐项结论；不得以“未运行”默认通过。像素差异的忽略区域、阈值和原因必须在测试证据中明确，禁止用宽泛遮罩掩盖布局差异。

## 9. Codex 修复循环

发现视觉偏差时，必须按以下闭环执行：

1. 固化问题截图、原型参照、路由、viewport 与精确 Commit SHA。
2. 以 HTML/CSS/组件对照定位根因，明确属于实现偏差、接口/权限缺口或原型/需求变更。
3. 只做最小范围修复；接口或产品范围问题先走变更控制，不用视觉替代方案掩盖。
4. 运行相关测试、构建与 `git diff --check`。
5. 重新截图并与原型对照；未通过则继续循环，不得因已部署而停止。
6. 记录修复证据、遗留差异和未验证原因；只有满足第 10 节才能标记页面完成。

## 10. 页面完成判定标准

页面仅在以下条件全部满足时可标记为“原型还原完成”：

- 已完成第 3 节逐项 HTML/组件对照；
- 目标 viewport 截图对照通过，未发现未批准的可见差异；
- 原型的模块、组件、卡片、字体层级、资源与关键交互均完整，且没有原型外可见内容；
- 真实 API、权限、加载、空态和错误态已按批准边界接入；
- 相关前端测试、生产构建和 `git diff --check` 通过；
- 证据已记录到 `06-testing/`，并绑定精确 Commit SHA；
- 项目负责人需要人工确认时，ECS 测试环境运行的版本与证据 SHA 一致。

不满足任何一项时，状态只能是“整改中”“待视觉验收”或“受接口缺口阻断”，不得宣称完成、验收通过或解锁后续 Stage。
