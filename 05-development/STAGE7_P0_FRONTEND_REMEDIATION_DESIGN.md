## 1. 问题与目标

当前 `codebase/frontend/` 只有四个业务路由，工作台和其他页面为最小表单/页面壳；它没有实现已批准 Stage 3 原型的完整信息架构、页面布局、关键组件和交互状态。该差异是实现偏离，不是原型、PRD、SPEC 或验收标准变更。

本修复目标是：在独立 React/TypeScript 正式前端中，以 `03-ui-prototype/prototype/` 为只读视觉和交互参考，完整实现页面功能矩阵中的全部 P0 页面；所有业务事实、权限和状态均来自已批准后端 API，或由明确登记的 Stage 5 后端契约修复提供。

## 2. 范围与非目标

### 范围

1. 登录、全局侧栏、顶部栏、通知、用户入口、权限驱动导航和全局 Agent 抽屉。
2. 工作台、驾驶舱 BI、工厂建模、设备台账、设备新增/编辑/详情、故障上报及接单前诊断、Agent 上报、维修记录、维修执行、系统管理和智能配置。
3. 每个 P0 页面对应的默认、加载、空态、错误、禁用、权限拒绝和已批准的关键边界状态。
4. 原型中的布局层级、视觉令牌、表格/卡片/筛选/抽屉/对话结构及已批准交互；正式实现使用 React 组件和真实服务响应。
5. “原型页面 → 正式路由 → API 契约 → 自动化测试 → 浏览器验收证据”的可追溯矩阵。

### 非目标

- 不复制、导入或运行静态原型 HTML/JavaScript/CSS。
- 不改写 Stage 1—3 基线、业务规则、权限规则、验收标准或原型本身。
- 不以静态演示数据、伪造健康分、伪造引用或假成功状态填充正式页面。
- 不新增生产依赖；若视觉回归工具需要新开发依赖，须先单独确认。
- 不在本次修复中启动 Stage 8、`main` 合并或生产部署。

## 3. 正式信息架构

| 原型范围 | 正式路由/组件 | 数据与权限边界 |
| --- | --- | --- |
| Login | `/login` | 会话 API；登录/加载/禁用/失败状态 |
| Workbench | `/` | 待办、告警、健康和快捷动作均只消费服务端数据 |
| 驾驶舱 BI | `/bi-dashboard` | 管理摘要、趋势、排行、全局筛选；无对应契约时先回流后端 |
| 工厂建模 | `/factory-modeling` | 组织树、搜索、展开、CRUD 与级联权限 |
| 设备台账 | `/equipment` | 列表、筛选、权限、加载/空/错状态 |
| 设备新增/编辑/详情 | `/equipment/new`、`/equipment/:id/edit`、`/equipment/:id` | 设备 API、负责人、健康和历史数据 |
| 故障上报与接单前诊断 | `/fault-report` | 人工上报、AI 草稿、诊断、引用、采纳/直接开始、附件失败重试 |
| Agent 上报及全局 Agent | `/agent-report` 与全局抽屉 | Agent 线程、SSE、权限、对话历史隔离 |
| 维修记录 | `/maintenance-records` | 维修列表、详情、知识沉淀状态 |
| 维修执行 | `/repair-execution` | 工单接单、诊断摘要、维修结果和权限 |
| 系统管理 | `/system-management` | 用户、角色、菜单/操作权限、审计及 self-only 边界 |
| 智能配置 | `/intelligent-config` | 模型资源、四个 Agent、知识流程、调用记录和只读指标 |

共享应用壳负责渲染导航和全局状态；页面组件只负责页面组合与交互；`src/api.ts`（或同等小型领域 API 模块）继续是 HTTP/SSE 边界。页面不得自行拼接 Token、业务事实或 Agent 推理结果。

## 4. 视觉与交互实现原则

1. 从原型提取并在正式样式中实现色彩、间距、圆角、排版、卡片、表格、标签、按钮、抽屉和响应式规则；不复制原型源码。
2. 侧栏、顶部栏、通知与用户入口只实现一次，由所有路由共享；导航必须按当前会话权限显示和保护。
3. 页面布局先与原型的内容层级和操作优先级一致，再绑定真实 API；禁止先创建“看起来完整”的静态数据页面。
4. 所有写操作呈现验证中、保存中、成功和失败；所有列表/指标明确呈现加载、空、错误与重试。
5. Agent 仅显示服务端实际返回的 SSE 状态、摘要和引用；`NO_EVIDENCE`、`UNAVAILABLE`、权限拒绝和人工路径必须有与原型一致的可见反馈。

## 5. API 契约缺口处理

现有前端 API 客户端主要覆盖登录、故障、维修、Agent、健康分和智能配置；全部 P0 页面需要先完成一次 API 对照。对每一项采用以下规则：

- 已存在且符合规格：正式前端直接接入，并用真实错误/权限响应驱动状态。
- 已存在但响应不足以支撑批准页面：登记明确契约缺口，回流 Stage 5 后端修复，随后接入。
- 不存在：不得以 mock、硬编码卡片或伪造数据替代；登记为 Stage 5 后端子任务并由任务书定义负责人、审核和依赖。

这确保视觉还原不会掩盖业务能力缺失。

## 6. 实施顺序

1. 建立页面/API/状态差异矩阵，登记每项可用接口和缺口；补充 Stage 5 修复任务书。
2. 实现共享视觉令牌、应用壳、权限导航、用户/通知入口与全局 Agent 抽屉，并完成跨页回归。
3. 实现设备与组织域页面：工作台、BI、工厂建模、设备台账及设备新增/编辑/详情；并同步关闭必要 API 缺口。
4. 实现现场作业与 Agent 页面：故障上报、Agent 上报、诊断、维修执行、维修记录和全局 Agent。
5. 实现治理与配置页面：系统管理、智能配置及其权限/错误状态。
6. 以页面矩阵完成逐页浏览器对照、可访问性与真实 API 回归，建立新的 Stage 6 测试候选；Stage 7 只在新候选获批后恢复。

每一项稳定页面/垂直切片均创建可恢复功能检查点，避免大范围前端返工失去可回退边界。

## 7. 验证与完成条件

完成本修复前必须具备：

- 页面矩阵中全部 P0 页面、路由、角色、关键状态和原型参考已逐项映射。
- 前端单元/交互测试覆盖真实数据、加载、空态、错误、权限和关键 Agent/维修边界。
- 前端生产构建、相关后端测试、静态检查和 `git diff --check` 通过。
- 在隔离浏览器环境完成逐页视觉/交互对照，证据记录具体候选 SHA、浏览器、视口、页面/状态、结果和缺陷。
- RAGFlow、Docker 和其他 live-stack 验证只由具备环境的责任人执行；未验证项目不得写为通过。
- 无演示数据、原型运行时依赖、未授权生产依赖、无关重构或未记录 API 缺口。

## 8. 风险、回退与阶段门

- 风险：页面范围大，现有后端接口覆盖可能不足；必须以 API 差异矩阵确定真实工作量，而非承诺单一前端提交即可完成。
- 回退：按共享壳和每个页面/领域的独立可恢复提交选择性 revert；不得回退或删除已完成的非前端功能。
- 阶段：Stage 7 验收对受影响页面保持阻断。修复按 Stage 5 任务书审核、集成和项目负责人逐 PR 授权；合并后重新执行受影响的 Stage 6 与 Stage 7 证据。
