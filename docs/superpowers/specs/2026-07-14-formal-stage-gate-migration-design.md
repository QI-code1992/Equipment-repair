# 正式 Stage-Gate 接管与资料补齐设计

- 日期：2026-07-14
- 状态：已获用户批准，等待书面规格复核
- 仓库：`QI-code1992/Equipment-repair`
- 适用流程：`formal-software-delivery-workflow`

## 1. 背景与目标

当前工作区是一个由历史 PRD/SPEC、规则覆盖文件、流程图、静态 HTML 原型、AI 技术说明、实施计划和原型静态检查组成的交接包。它具备较完整的产品认知，但缺少唯一有效的正式基线、阶段审批记录、完整工程架构和可审计的版本历史。

本次接管要实现两个目标：

1. 合并最新规则与历史 PRD/SPEC，形成唯一的 Stage 1 PRD、SPEC、验收标准和需求追踪矩阵。
2. 以当前静态原型为候选设计证据，补齐 Stage 0–8 的正式资料骨架和已知内容，为后续开发、测试、验收与发布建立可持续版本管理体系。

## 2. 方案比较与选择

### 方案 A：先快照、再迁移（采用）

先将原始工作区提交并创建不可变恢复标签，再把当前有效内容迁入编号阶段目录。历史冲突文件不保留为本地有效副本，统一通过 Git 标签恢复。

- 优点：恢复边界清晰；本地最终只保留当前有效状态；符合正式流程的版本控制规则。
- 代价：迁移提交较大，需要严格检查引用和运行路径。

### 方案 B：保留旧目录并新增正式副本（不采用）

保留 `docs/`、`prd/`、`diagrams/` 等目录，同时复制内容到阶段目录。

- 优点：短期路径变化少。
- 缺点：形成多份“当前版本”，后续极易再次出现基线冲突，不符合单一规范文件原则。

### 方案 C：直接清理后首提（不采用）

先删除重复和历史内容，再把整理后的目录作为 Git 首次提交。

- 优点：首个版本整洁。
- 缺点：丢失接管前状态，不利于审计和回滚。

用户已批准方案 A。

## 3. 版本控制设计

### 3.1 原始恢复点

- 原始导入 Commit：`c544c2d`
- 恢复标签：`snapshot/legacy-import-20260714`
- 标签用途：恢复或对照正式化整理前的完整资产，不作为任何阶段审批基线。
- 排除内容：`.DS_Store`、`.superpowers/` 临时状态、日志、PID、环境密钥和构建产物。

### 3.2 正式提交边界

正式化工作至少拆分为以下可审计提交：

1. 接管设计与治理状态。
2. Stage 1 唯一需求基线候选包。
3. Stage 0、Stage 2–4 候选资料与原型迁移。
4. Stage 5–8 真实状态资料、根入口和验证工具。
5. 验证修正与最终候选基线整理。

阶段审批通过后另行创建不可移动的 `baseline/stage-XX-...-v1.0` 注释标签。本次资料补齐不能自动创建阶段基线标签。

## 4. 目录与资产迁移设计

正式目录采用：

```text
00-opportunity/
01-requirements/
02-product-interaction-design/
03-ui-prototype/
04-architecture-plan/
05-development/
06-testing/
07-acceptance/
08-release-handoff/
workflow/
tests/
README.md
```

迁移规则：

- 每个正式制品只保留一份当前规范文件。
- 历史 PRD/SPEC、覆盖说明、旧计划和重复 PDF 在正式化提交中移出当前工作区；通过原始标签追溯。
- 当前可运行原型迁移到 `03-ui-prototype/prototype/`，保留其源文件和页面结构。
- XMind/JSON 流程源文件迁入 Stage 2 的 `assets/`，并以 Markdown 规范文件描述当前有效流程。
- AI 技术 SPEC 作为 Stage 4 输入，合并到系统架构、API、数据模型和 ADR，而不是继续充当独立最高依据。
- 原型静态检查保留在 `tests/`；与当前基线冲突的测试按正式需求修改，并在测试报告中记录原冲突。

## 5. Stage 1 合并规则

### 5.1 权威来源顺序

合并时按以下优先级裁决：

1. `docs/开发交付入口.md`
2. `docs/PRD-当前有效版.md`
3. `docs/今日对接结论.md`
4. `docs/开发基线说明.md`
5. `docs/superpowers/specs/2026-07-13-health-score-and-permission-prototype-sync-design.md`
6. 历史完整 PRD、SPEC、流程图和原型中不冲突的内容

### 5.2 必须固化的已确认规则

- 健康分基础分 100、最低 0；正式上线日从 100 分起算，不回算上线前数据。
- 当前评分周期 30 天，变化快照展示 60 天。
- 风险等级为：100 正常、80–99 低风险、60–79 中风险、40–59 高风险、0–39 严重风险。
- 状态扣分、当前紧急程度、逾期风险和重复故障风险独立叠加。
- 停用设备冻结评分；存在待接单或维修中故障时禁止停用。
- SLA 从故障正式提交起算，非常紧急、紧急、一般分别为 2/4/6 小时。
- 一期故障状态仅为待接单、维修中、已处理，不支持重新打开。
- 仅提交人可删除待接单故障，且保留审计日志。
- 智能问数仅使用 40 项内置指标和允许维度，模型不计算或猜测数值，指标管理只读。
- RAGFlow 负责知识解析、检索、重排与引用；业务数据库是事实源。
- LangGraph 负责受控 Agent 编排，不得绕过业务 API 或直接修改健康分。
- 固定角色为系统管理员、设备管理员、维修工、产线作业员。
- 系统只建设菜单与操作权限；仅保留 Agent 场景中的既有设备授予边界，不扩展为通用数据权限。
- 数据导入不属于一期开发范围，历史页面只保留在原始快照中。
- 单附件上限 100MB；初始数据手工录入。
- 演示环境为 Windows；临时外网访问使用 Tailscale Funnel；每天 00:10 备份并保留 10 天。

### 5.3 Stage 1 输出

- `01-requirements/PRD.md`
- `01-requirements/SPEC.md`
- `01-requirements/ACCEPTANCE_CRITERIA.md`
- `01-requirements/REQUIREMENTS_TRACEABILITY_MATRIX.md`

四份文件均标记为 `Candidate v1.0`，直到用户显式批准 Stage 1。

## 6. 各阶段资料补齐边界

### Stage 0

根据现有材料整理问题、目标用户、价值、替代方案、可行性、风险和 MVP 验证路径。缺少真实市场调研证据时明确标记为“资料不足”，不虚构竞品数据。

### Stage 2

从 PRD/SPEC、流程图和原型提取业务流程、用户流程、页面功能矩阵、交互状态、异常路径和原型覆盖。页面存在但已退出范围的功能不得进入当前矩阵。

### Stage 3

以现有静态原型为候选视觉与交互基线，记录设计原则、令牌、组件、覆盖关系和恢复方法。原型未覆盖的 loading、empty、error、permission 等状态必须列为缺口，不假定已完成。

### Stage 4

以软件系统、LangGraph、RAGFlow 三边界为核心，补齐系统上下文、模块、数据流、信任边界、API、数据模型、ADR 和实施计划。具体生产技术栈尚未确认的部分以“决策门禁”描述，不擅自选型。

### Stage 5

只创建开发说明、自测、评审、提交和检查点台账。当前没有生产实现，因此状态必须为 `Not Started`，不得把静态原型标记为开发完成。

### Stage 6

基于 Stage 1 AC 建立测试计划与测试用例；原型检查结果与生产验收结果分开。未执行的生产检查标记为 `NOT RUN`，已知冲突登记为缺陷或基线修正项。

### Stage 7

建立验收报告和证据结构，但在没有用户批准的精确 Commit SHA 前保持 `BLOCKED`，不得给出 `ACCEPTED`。

### Stage 8

根据已知 Windows 演示约束整理候选运行手册、部署、回滚、发布说明和交接；缺少生产实现的步骤明确标记为待 Stage 5/6 补充。

## 7. 一致性与验证设计

验证至少包括：

- JSON 文件语法检查。
- Markdown 内部路径和正式制品引用检查。
- 需求 ID、AC ID、测试用例 ID 的追踪闭环检查。
- 全仓库废弃规则扫描。
- 原型 HTTP 启动与关键页面 200 检查。
- 所有现有 Node 静态检查执行与结果统计。
- Git 工作区清洁、提交可达、远端分支和原始恢复标签检查。

验证失败时保持阶段候选状态，不通过修改需求来让实现或测试“变绿”。

## 8. 风险与控制

| 风险 | 控制 |
|---|---|
| 历史规则被误带入当前基线 | 权威来源优先级、废弃规则扫描、需求追踪矩阵 |
| 迁移导致原型路径失效 | 独立迁移提交、HTTP 冒烟检查、原始恢复标签 |
| 补齐资料被误认为阶段已通过 | 文件显式标记 Candidate/Not Started/BLOCKED，审批台账不写 Approved |
| 未知技术栈被擅自确定 | Stage 4 使用决策门禁和 ADR 候选，不虚构既定技术方案 |
| 历史材料丢失 | 原始 Commit 与注释标签已建立并推送 GitHub |
| 远端版本与本地不一致 | 每次交付核对远端 SHA、标签和工作区状态 |

## 9. 完成定义

本次资料正式化在以下条件同时满足时完成：

- 所有规定阶段目录和必需文件存在。
- Stage 1 四件套内部一致，需求、AC、测试和页面覆盖可追踪。
- 当前工作区只保留规范文件、当前原型、测试与必要证据；历史状态可从 GitHub 标签恢复。
- 原型仍可运行，验证结果如实记录。
- GitHub `main` 包含所有正式化提交，原始快照标签可达。
- `workflow/state.json` 与审批、变更、交接台账一致。
- 所有阶段仍保持候选或未执行状态，等待用户逐阶段审批。

## 10. 非目标

- 本次不开发生产后端、数据库、LangGraph 工作流或 RAGFlow 集成。
- 本次不替用户选择尚未确认的生产技术栈、模型供应商或设备型号。
- 本次不把静态原型测试提升为生产验收证据。
- 本次不自动批准任何 Stage-Gate。
