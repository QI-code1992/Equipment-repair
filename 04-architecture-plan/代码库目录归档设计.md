# 代码库目录归档设计

## 1. 状态与目标

- 状态：已确认方向，等待书面设计复核后实施
- 变更级别：L3（架构与开发路径基线变更）
- 目标：在保留 Stage 0—8 阶段交付目录的前提下，为正式源代码、运行配置和工程测试建立唯一、清晰的工程归档边界。

本设计解决两个问题：

1. 阶段交付物与长期演进的工程文件不能混放。
2. Stage 3 原型必须继续作为该阶段的正式交付物，不得复制到正式代码库形成两个事实来源。

## 2. 方案比较

### 方案 A：维持多个根级工程目录

保留根目录下的 `backend/`、`frontend/`、`infra/`。路径最短、工具兼容性最好，但根目录同时承载阶段档案、工程目录和治理目录，分类边界不够直观。

### 方案 B：建立统一 `codebase/` 目录（采用）

把正式后端、正式前端、基础设施和跨系统工程测试归入 `codebase/`。阶段交付物仍位于编号目录，跨阶段治理文件仍位于 `workflow/`。该方案最符合“所有非阶段工程文件统一归档”的目标。

### 方案 C：把工程文件放入 `05-development/`

不采用。`05-development/` 用于开发过程记录、检查点、自测和代码评审材料；正式代码会跨越开发、测试、验收、发布和长期维护，不应成为 Stage 5 的阶段档案。

## 3. 目标目录结构

```text
<project-root>/
├── 00-opportunity/
├── 01-requirements/
├── 02-product-interaction-design/
├── 03-ui-prototype/
│   └── prototype/              # Stage 3 原型唯一事实来源
├── 04-architecture-plan/
├── 05-development/
├── 06-testing/
├── 07-acceptance/
├── 08-release-handoff/
├── workflow/                   # 跨阶段状态、审批、变更与交接台账
├── codebase/                   # 正式工程文件
│   ├── backend/                # 后端代码、后端构建文件及后端单元测试
│   ├── frontend/               # 正式前端代码、前端构建文件及前端单元测试
│   ├── infra/                  # Docker、Nginx、环境模板、部署与运维脚本
│   └── tests/                  # 可选：跨服务、端到端工程测试
├── .github/                    # 可选：GitHub Actions 与仓库自动化
├── .gitignore
└── README.md
```

目录名使用稳定英文标识 `codebase/`，中文名称“代码库”仅用于文档说明，降低 Docker、CI、Shell 和跨平台工具处理路径时的兼容风险。

## 4. 强制归档规则

### 4.1 Stage 3 原型

- 高保真页面、HTML/CSS/JavaScript 演示代码、原型专用资源和交互演示保留在 `03-ui-prototype/prototype/`。
- `03-ui-prototype/prototype/` 是原型的唯一事实来源，不得复制到 `codebase/prototype/`。
- Stage 5 可参考已批准原型实现正式前端，但正式产品页面只能以 `codebase/frontend/` 为事实来源。
- 原型变更继续通过 `03-ui-prototype/PROTOTYPE_CHECKPOINTS.md` 和 Stage 3 基线管理。

### 4.2 正式工程文件

- `backend/` 迁移为 `codebase/backend/`。
- `frontend/` 迁移为 `codebase/frontend/`。
- `infra/` 迁移为 `codebase/infra/`。
- 服务自身测试跟随服务，例如 `codebase/backend/tests/` 和 `codebase/frontend/**/__tests__/`。
- 真正跨服务的端到端工程测试可放在 `codebase/tests/`，没有此类测试时不创建空目录。

### 4.3 Stage 6 测试材料

- 测试计划、测试用例说明、缺陷台账、测试报告和回归报告继续位于 `06-testing/`。
- 当前 `06-testing/tests/` 中用于验证 Stage 3 原型基线的静态检查继续保留在 Stage 6，不随生产代码迁移。
- 后续生产自动化测试优先与被测服务共置；其执行结果和验收证据归档到 `06-testing/`。

### 4.4 其他非阶段文件

- 只有跨阶段治理文件可放在 `workflow/`。
- 仓库入口和仓库级控制文件保留在根目录，例如 `README.md`、`.gitignore` 和 `.github/`。
- 不再建立通用 `docs/` 作为正式文档堆放区；现有内容应判断所属阶段后迁入对应编号目录，无法归属且只是临时材料的文件不得作为正式基线保留。
- 真实密码、Token、私钥、生产 `.env` 和容器卷数据不得提交；仅环境变量模板可进入 `codebase/infra/`。

## 5. 路径迁移范围

实施时至少同步更新以下引用：

- `04-architecture-plan/AGENTS.md`
- `04-architecture-plan/IMPLEMENTATION_PLAN.md`
- `05-development/` 中的开发记录、检查点、自测和工作包
- `06-testing/`、`08-release-handoff/` 与 `workflow/` 中的工程路径
- `README.md`
- Docker Compose 的构建上下文及环境文件调用路径
- 后端、前端、测试、CI/CD 和本地运行命令

迁移必须使用 Git 可识别的重命名，不能保留旧目录兼容副本。若存在外部调用方仍依赖旧路径，必须先记录真实调用方、迁移窗口和旧路径删除条件；当前未发现需要旧路径兼容的外部调用方。

## 6. 工作流技能约束

`formal-software-delivery-workflow` 应增加以下强制规范：

1. 阶段产生的文档或交付物必须归入对应编号阶段目录。
2. 跨阶段治理文件只能放入 `workflow/`。
3. 正式源代码、基础设施配置及工程测试可统一归入根级 `codebase/`；不得放入 `05-development/`。
4. Stage 3 原型及原型专用资源必须保留在 `03-ui-prototype/`，不得移入或复制到 `codebase/`。
5. 正式前端与 Stage 3 原型必须各自只有一个事实来源，禁止双份同步维护。

## 7. 验证与完成标准

迁移完成必须满足：

- 根目录不再存在旧的 `backend/`、`frontend/` 和 `infra/`。
- `03-ui-prototype/prototype/` 路径与内容保持不变。
- 所有受影响的文本路径引用已迁移，无失效旧路径。
- 后端最小相关测试通过。
- 原型静态回归检查通过。
- Docker Compose 配置校验通过；若执行环境缺少 Docker，必须如实列为未验证项。
- `git diff --check` 通过，完整 diff 中不包含无关修改。
- 不增加生产依赖、兼容代码或多余抽象层。

## 8. 回退方式

本次迁移应形成独立提交。若验证失败，优先通过该提交的反向变更恢复目录及引用，不使用破坏历史的强制重置。Stage 3 原型路径不得参与回退迁移。
